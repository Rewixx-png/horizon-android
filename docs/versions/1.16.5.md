# Minecraft Java 1.16.5: a second Rust target

This branch starts from the 26.3 Android client. It is **not** a downloader
mode: supporting 1.16.5 means a second native engine target with its own
protocol, registries, world format, assets and gameplay. No Java runtime is
involved, and Fabric/Forge/NeoForge/OptiFine JARs remain out of scope.

## What can be shared

- `horizon-client-render`: wgpu renderer, HUD, screens, input plumbing.
- `horizon-client-input`, window/clipboard/controller abstractions.
- `horizon-assets` where the 1.16.5 model/atlas formats match.
- The Android launcher shell, language/theme, updater and release workflow.
- Network framing and transport, with a 1.16.5 packet layer.

## What must be version-specific

- Version constants and data-version gates.
- Block/item/entity/registry tables. 1.16.5 predates item components and the
  1.17 world-height changes; do not reuse 26.3 tables.
- Protocol 754: handshake, status, login, configuration is not a separate
  phase in 1.16.5, and the play packet set differs throughout.
- World load/save, chunk sections, biomes, worldgen and the Nether.
- Resource-pack format 6, models, languages, sounds.
- UI screens and option semantics where vanilla changed.

Prefer small version modules behind explicit traits over copying whole 26.3
modules. Each divergence should be justified by a 1.16.5 reference or a
differential harness, not by "it looks old".

## Milestones

**M0 - inputs and tables.** Extend the prepare pipeline to fetch and verify
the 1.16.5 client/server/asset set, emit 1.16.5 tables, and add a lock file.
Acceptance: prepared tables contain the version's blocks/items/registries;
no game code changes yet.

**M1 - protocol 754.** Status and login against a local 1.16.5 server, then
join and hold a connection. Acceptance: recorded handshake/login/play bytes
match the vanilla oracle; a bot can join and see keep-alives.

**M2 - world and frame.** Load a 1.16.5 world, render blocks with format-6
assets, and run the integrated server path. Acceptance: a deterministic
fixture world renders and survives save/load.

**M3 - player loop.** Movement, collision, block break/place, inventory,
containers and crafting. Acceptance: parity harnesses for those areas.

**M4 - content.** Mobs, worldgen, dimensions/Nether, entities, effects and
combat. Acceptance: named parity suites pass on both engines where behavior
is shared.

**M5 - packaging.** Android build, saves/datafixers, and only then a version
picker. Acceptance: the picker lists only engines that actually launch; no
download button for an unimplemented runtime.

## Packaging decision

Prove 1.16.5 as a separate APK/target first. A single APK with two engines is
possible but doubles native code and assets; decide only after M2, using APK
size, startup time and maintenance cost as the criteria. Never download
native code or an engine at runtime; ship it in an APK.

## Risks

- The 26.3 engine is a massive parity implementation; 1.16.5 is another port,
  not a branch of a few constants.
- Protocol, world and asset differences touch most modules.
- Two targets multiply test, build and support cost.
- Android thermal/memory limits make a second engine in one APK expensive.
