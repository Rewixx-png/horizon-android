# Minecraft Java 1.16.5: a second Rust target

This branch starts from the 26.3 Android client. It is **not** a downloader
mode: supporting 1.16.5 means a second native engine target with its own
protocol, registries, world format, assets and gameplay. No Java runtime is
involved, and Fabric/Forge/NeoForge/OptiFine JARs remain out of scope.

## Status (2026-10-31)

**M0 complete.** `docs/versions/1.16.5.lock.json` pins the client, server,
both mapping files and the 1.16 asset index. `tools/prepare_1165.py` verifies
every SHA-1, runs Mojang's own `net.minecraft.data.Main --reports` generator,
and writes a checked private bundle to `.local/versions/1.16.5/`:

```sh
python3 tools/prepare_1165.py                 # download, verify, generate tables
python3 tools/prepare_1165.py --verify-only   # re-check an existing bundle
python3 tools/prepare_1165.py --assets        # also verify/download the 334 MB asset set
```

The generated `tables.json` contains, for 1.16.5:

| Table | Count |
|---|---:|
| blocks | 763 |
| block states (global ids) | 17 112 |
| items | 976 |
| registries | 46 |
| biomes | 79 |

The tool rejects a different protocol/world version, duplicate state or
protocol ids, missing/multiple default states, block-report/registry drift,
and any count drift from the lock. `tests/test_prepare_1165.py` covers those
checks without the network. Inputs and tables stay under `.local/`; no Mojang
file is committed.

**M1 network slice (offline mode) complete.** `horizon_protocol::v1_16_5`
implements protocol 754 status ping, compression, offline login and the play
keep-alive exchange. It was verified against a real local 1.16.5 server:

```sh
cargo test -p horizon-protocol v1_16_5
HORIZON_1165_SERVER=127.0.0.1:25566 \
  cargo test -p horizon-protocol v1_16_5::tests::live_status_login_and_hold -- --ignored --nocapture
```

The live test pings the server, logs in as an offline player, receives play
packets, answers keep-alives and holds the connection for 17 seconds. Online-mode
encryption, the rest of the 1.16.5 play packet set, and everything from M2 on
are not implemented. The module is a protocol slice, not a launcher option:
there is no version picker and no server entry that would imply a playable
1.16.5 world yet.

**M2 first slice (world data).** `horizon_protocol::v1_16_5` now parses
Join Game, Chunk Data (palette-packed sections, global state ids, biomes and
block-entity NBT), resolves section block ids, and keeps loaded columns in a
`World`. `Tables::load` indexes the M0 `blocks.entries` by 1.16.5 state id.
The live test above now also parses the first Join Game and Chunk Data from the
real server, asserts the overworld dimension, 1024 biome cells and a present
section, and—when `HORIZON_1165_TABLES` is set—resolves the first block through
the prepared table:

```sh
HORIZON_1165_TABLES=.local/versions/1.16.5/tables.json \
  cargo test -p horizon-protocol v1_16_5::tests::live_status_login_and_hold -- --ignored --nocapture
```

This is **not M2 acceptance yet**: there is no 1.16.5 world file reader,
format-6 resource loader, chunk mesher, frame, or integrated server, so no APK
or launcher entry is exposed. The remaining M2 work is the first one that
produces a visible frame.

**M2 data/frame slice (in progress).** The new `horizon-1-16-5` crate now
separates the version target from the 26.3 engine:

- `world::World::open` reads real 1.16.5 Anvil regions, 16-block sections,
  1.16.x padded palette packing, biomes and empty sections (including the
  empty `Y=-1` section 1.16.5 writes in flat worlds).
- `assets::ModelPack` loads format-6 blockstates/models directly from a
  resource pack's `assets/minecraft` tree, resolves parents/texture variables,
  variants/multipart, UV locks and element rotations, and implements
  `ModelSource`. `load_lenient` skips individual malformed models like vanilla
  does instead of rejecting the whole pack.
- `mesh::mesh_box` turns named states plus baked models into a deterministic
  CPU `Mesh` with per-quad texture names and face culling.
- `preview` software-rasterizes a mesh to PPM; `examples/preview_world.rs`
  loaded a real 1.16.5 world and the vanilla model pack, rendered a chunk
  (9,336 vertices / 14,004 indices) and wrote an 800×600 image. This is a
  debug frame, **not** the game renderer.
- Protocol 754 now also decodes Player Position/Look, Chat, Disconnect and
  encodes Teleport Confirm.

**M2 first real frame (offscreen).** The crate now turns a CPU chunk mesh into
an actual GPU frame without touching the 26.3 client:

- `atlas::TextureAtlas` packs the format-6 sprites a mesh references, reading
  `assets/objects` through the 1.16 index first and falling back to
  `client.jar`. `client.jar` also supplies the blockstates and models through
  `ModelPack::load_client_jar`, so no extracted pack is needed. Animated
  textures use the first frame named by `frameHeight` in their `.png.mcmeta`;
  unknown names use the generated magenta/black `missingno` sprite.
- `render::OffscreenRenderer` creates its own wgpu instance, device, depth
  buffer and pipeline, draws the mesh with nearest-neighbour atlas sampling,
  reads the RGBA8 target back and writes a PNG. It is a diagnostic image, not
  the game renderer: fixed directional light, alpha cutout instead of
  blending, no sky, entities, HUD or shaders.
- `examples/render_world.rs` runs the whole path on a real 1.16.5 world.

Verified against the private bundle (flat 1.16.5 world with oak, bricks,
stone bricks, glass, wool, grass and iron around spawn):

```sh
cargo test -p horizon-1-16-5
cargo test -p horizon-1-16-5 --test first_frame -- --ignored --nocapture
cargo run -p horizon-1-16-5 --example render_world -- \
  --world .local/versions/1.16.5/world \
  --tables .local/versions/1.16.5/tables.json \
  --client-jar .local/versions/1.16.5/inputs/client.jar \
  --assets-index .local/versions/1.16.5/inputs/assets/indexes/1.16.json \
  --assets-objects .local/versions/1.16.5/inputs/assets/objects \
  --out frame.png
```

**M2/M3 playable desktop slice.** The crate now has a real windowed
loop: `app::run` (binary `horizon-1165`) loads the world, format-6 models and
vanilla textures, builds a multi-chunk mesh, ticks an integrated server at
20 Hz and draws a first-person view through `render::SurfaceRenderer`.

```sh
cargo build --profile fast -p horizon-1-16-5 --bin horizon-1165
target/fast/horizon-1165 \
  --world .local/versions/1.16.5/world \
  --tables .local/versions/1.16.5/tables.json \
  --client-jar .local/versions/1.16.5/inputs/client.jar \
  --assets-index .local/versions/1.16.5/inputs/assets/indexes/1.16.json \
  --assets-objects .local/versions/1.16.5/inputs/assets/objects
```

Controls: W/A/S/D, Space jump, Shift sprint, Ctrl sneak, mouse look, left
click break, right click place, 1-9 hotbar, wheel scroll, Escape release the
cursor then exit. `--spawn x y z`, `--radius <chunks>` (default 4), `--width`,
`--height` and `--frames N` (exit after N presented frames, for harnesses) are
accepted.

What is implemented: mutable block sections, air/stone-style placement,
axis-separated AABB collision with 0.6 step-up, a nine-slot creative hotbar,
DDA block picking with 5-block reach, chunk remeshing around the player, and
break/place through the same `World` the server ticks. Baked models are cached
per block state, grass/leaves get the plains tint, glass/water/ice quads draw
in a separate alpha-blended pass, chunk meshes are rebuilt on a background
worker from a captured snapshot, and edited chunks are written back in place
with `World::save`: every 30 seconds while running, on window close and in
winit's `exiting` callback. The save keeps every non-section tag of the chunk
it replaces (heightmaps, entities, tile entities, ticks, structures), so
vanilla can still open the world. The HUD hotbar samples the real block
textures from the atlas as colour bands. On Android the extracted tree has a
`.ready` marker, so an app restart reuses the saved world instead of
overwriting it with the APK copy.

Verified with `cargo test -p horizon-1-16-5` (144 unit tests), the ignored
`tests/play_slice.rs` on the private world (spawn/fall/walk, break+place,
save/reopen, first-person PNG), a real `horizon-1165` window under Xvfb
(`--frames 2` → `rendered 2 frames`), and `xdotool` holding W for three
seconds (the presented frame changed by 94,910 pixels).

Still open: this is a development slice, not a release. Physics and collision
are approximations (full cubes, no slabs/stairs/water movement), there is no
inventory screen or crafting, hotbar icons are eight-band approximations
rather than crisp sprites, and there are no mipmaps or UV wrapping outside a
sprite. Mobs, worldgen, entities, the Nether/End, sound, and the Android
UI/version picker are still missing.

**Android developer APK (arm64).** A separate app, not the 26.3 launcher and
not a public release, packages the native 1.16.5 loop and its private inputs:

```sh
python3 tools/android_build_1165.py --abi arm64-v8a \
  --gradle /opt/gradle/gradle-8.14.3/bin/gradle
```

The APK is `dev.horizon.android1165` (`Horizon 1.16.5 Dev`), with one
`libhorizon_1_16_5.so` and `assets/1165.zip` holding `world/`, `tables.json`
and `client.jar` from `.local/versions/1.16.5`. Nothing Mojang enters Git. At
startup the NativeActivity entry extracts the zip to the app's private data
directory and runs the same windowed loop; textures come straight from the
bundled client jar. The chunk radius is 2 on Android.

Touch controls: the left side is a virtual joystick (tap it to jump), the
right side is look (tap to break), the bottom-right button places the selected
block, and the nine-slot hotbar above the joystick selects a block on tap. A
crosshair, the control rectangles and the hotbar are drawn as a screen-space
HUD. Keyboard/mouse still work when connected.

Verified here: aarch64 `cargo check`, Gradle `assembleDebug`, apksigner v2
verification, aapt2 badging (`dev.horizon.android1165`, landscape
NativeActivity, minSdk 28), ELF `android_main` in the stripped arm64 library,
and the asset/native-library contents. This environment has no Android device
or emulator, so the APK has not been run on hardware; emulator FPS claims are
not phone FPS.

`.github/workflows/android-1165-apk.yml` builds the same APK on pushes to
`1.16.5` and on manual dispatch: it prepares the pinned inputs, generates the
flat fixture world with `tools/make_1165_fixture.py`, builds with
`tools/android_build_1165.py`, uploads the APK as an artifact and creates a
**draft** release. The draft is deliberate: the APK contains the private
client jar and world, so it must not be published as a public redistribution
until resource delivery moves to the device, as the public 26.3 packaging
does.

## What can be shared

- `horizon-client-render`: wgpu renderer, HUD, screens, input plumbing.
- `horizon-client-input`, window/clipboard/controller abstractions.
- `horizon-assets` where the 1.16.5 model/atlas formats match.
- The Android launcher shell, language/theme, updater and release workflow.
- Network framing and transport, with a 1.16.5 packet layer.

## What must be version-specific

- Version constants and data-version gates.
- Block/item/entity/registry tables. 1.16.5 predates item components and the
  1.17 world-height changes; do not reuse 26.3 tables.
- Protocol 754: handshake, status, login, configuration is not a separate
  phase in 1.16.5, and the play packet set differs throughout.
- World load/save, chunk sections, biomes, worldgen and the Nether.
- Resource-pack format 6, models, languages, sounds.
- UI screens and option semantics where vanilla changed.

Prefer small version modules behind explicit traits over copying whole 26.3
modules. Each divergence should be justified by a 1.16.5 reference or a
differential harness, not by "it looks old".

## Milestones

**M0 - inputs and tables.** Extend the prepare pipeline to fetch and verify
the 1.16.5 client/server/asset set, emit 1.16.5 tables, and add a lock file.
Acceptance: prepared tables contain the version's blocks/items/registries;
no game code changes yet.

**M1 - protocol 754.** Status and login against a local 1.16.5 server, then
join and hold a connection. Acceptance: recorded handshake/login/play bytes
match the vanilla oracle; a bot can join and see keep-alives.

**M2 - world and frame.** Load a 1.16.5 world, render blocks with format-6
assets, and run the integrated server path. Acceptance: a deterministic
fixture world renders and survives save/load.

**M3 - player loop.** Movement, collision, block break/place, inventory,
containers and crafting. Acceptance: parity harnesses for those areas.

**M4 - content.** Mobs, worldgen, dimensions/Nether, entities, effects and
combat. Acceptance: named parity suites pass on both engines where behavior
is shared.

**M5 - packaging.** Android build, saves/datafixers, and only then a version
picker. Acceptance: the picker lists only engines that actually launch; no
download button for an unimplemented runtime.

## Packaging decision

Prove 1.16.5 as a separate APK/target first. A single APK with two engines is
possible but doubles native code and assets; decide only after M2, using APK
size, startup time and maintenance cost as the criteria. Never download
native code or an engine at runtime; ship it in an APK.

## Risks

- The 26.3 engine is a massive parity implementation; 1.16.5 is another port,
  not a branch of a few constants.
- Protocol, world and asset differences touch most modules.
- Two targets multiply test, build and support cost.
- Android thermal/memory limits make a second engine in one APK expensive.
